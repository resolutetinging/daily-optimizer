Daily Optimizer 開發日誌 — 2026-07-03
====================================================================

問題一：AI 覆盤反饋與實際完成狀態矛盾（v2.8）
----------------------------------------------------------------
使用者反映：覆盤結果除了「閱讀」都完成，但 AI 生成的回饋卻說「今日
完成率低於預期，因為晚上沒有充分利用時間...水管過載的問題不是塞爆，
而是燃意志力不足」，且提到「晚餐」「逛書店」等資料中不存在的活動。

根因：水管過載判定（overloadedPipes）觸發時，prompt 原本無條件要求
AI 說「塞爆或燃意志力不足」，即使過載任務其實已完成
（doneCount===count），AI 仍被迫套用負面框架，導致與實際覆盤結果
矛盾，並連帶編造資料中不存在的活動。

修正：
1. 新增 allOverloadDone 判斷，過載但全部完成時改為「應點出配速是否
   可持續」，不可說塞爆/燃意志力不足；只有過載且真的未完成才用
   負面框架
2. 【狀態快照】指令加「必須與實際完成狀態一致，不可矛盾」
3. Prompt 加防幻覺護欄：嚴禁提及實際覆盤結果/AI預排任務/Calendar
   行程以外的任何活動名稱

問題二：睡眠戰力數值跟 Sleep Dashboard 對不起來（v2.9）
----------------------------------------------------------------
使用者發現 Sleep Dashboard「3夜加權」顯示 53，Optimizer「昨晚戰力」
卻顯示 45，且問「排除週末開關沒差是不是因為今天週五」。

診斷（先讀了 spec 才動手，這是使用者提醒後補做的步驟）：
sleep-dashboard-spec-v1.0.md 明文規定「debt 不可加 Math.max(0,...)
clamp」，但 Optimizer v2.6 引入的「平日戰力自算」
（isWeekendDate + calcNightRawOpt 篩選平日 7 夜自算 debt）的 debt
公式用了 Math.max(0, 480-total_min)，把每夜負債 clamp 在 0 以上，
好眠之夜的盈餘完全無法抵銷其他夜的負債——直接違反這條規則，導致
Optimizer 數值持續低於 Sleep Dashboard 本尊。

使用者決策：「optimizer combat 統一都 query sleep 三夜加權 →
平日接近事實；週末一般休假中也不衝突」——不再維護一份容易分歧的
獨立公式。

修正：showSleep() 移除整段平日自算邏輯（isWeekendDate、
calcNightRawOpt、debtPool、singleV 分支），改為統一直接讀
localStorage.sas_combat_weighted，找不到時 fallback 用當夜
rawScore（不算 debt）。

後續：Sleep Dashboard 那邊也重新定義了規格——單夜不受排除週末開關
影響，3夜加權受影響（開啟時只算週間資料）。Optimizer 現在讀到的
sas_combat_weighted 就是這個「受開關影響」的版本，符合使用者預期。

版本號更正
----------------------------------------------------------------
一開始把這兩個修正記憶檔標記為 v2.7/v2.8，事後發現 spec 早已有
v2.7（2026-07-02，AI反饋prompt範例移除）的既有記錄，造成版本號
撞號。已更正記憶檔與 spec 版本號為 v2.8（AI反饋矛盾）/v2.9（睡眠
戰力），並補上 daily-optimizer-spec-v1.0.md 原本漏記的這兩筆版本
紀錄。

教訓：涉及「公式/規則對不對」的問題，應優先讀 spec 而非自己用資料
反推規則；spec 才是版本號與規則的權威來源，不能只靠記憶檔自己編號。
